# Architecture

devhelper is a small Go application with two front doors:

- CLI commands in `internal/cli`
- a local HTTP UI/API in `internal/http`

Both front doors call the same provisioning layer, so project creation, deletion, cert generation, and SQL imports behave the same whether they come from the browser or the terminal.

## Package Map

- `cmd/devhelper`: process entrypoint.
- `internal/app`: repo-root detection, config loading, default config, logger setup.
- `internal/cli`: `urfave/cli` command definitions.
- `internal/http`: embedded web UI and JSON API routes.
- `internal/platform`: host/WSL path conversion, `.env` generation, hosts-file updates, file sync helpers, shell runner.
- `internal/provision`: project lifecycle, certs, database create/drop/import.
- `internal/store`: JSON-backed project metadata store.
- `internal/templates`: nginx vhost rendering.

## Config And Paths

The config file is `.devhelper-config.json` at the repository root.

On Linux/macOS, the default runtime root is the repository `projects` directory. On Windows, the runtime root defaults to `/data/projects` inside WSL, and `host_mirror_dir` points at the same location through `\\wsl$\Ubuntu\data\projects`.

The distinction matters:

- Docker and nginx use runtime paths such as `/data/projects/apps`.
- Go file operations on Windows use the UNC mirror path so they can create files inside WSL without shelling out.
- Docker Compose itself lives at `compose_dir`, a host path containing local `docker-compose.yml` and `.env`.
- The repository tracks `projects/docker-compose.example.yml`. The real `projects/docker-compose.yml` is generated by `devhelper init` if missing and then stays ignored.

`init` preserves the saved Compose directory and custom `.env` content. It
updates only a marked managed environment block, validates with Compose's dotenv
parser and safely escapes generated values. Config activation follows successful
Compose/environment preparation.

## Project Creation Flow

`provision.Create` performs these steps:

1. Sanitize company/project names into predictable slugs.
2. Expand the default domain pattern if no custom domain was provided.
3. Create the runtime app directory.
4. On Windows, create a tiny repo-side mirror folder with a `.wsl-path` breadcrumb.
5. Render and write the nginx vhost.
6. Add hosts-file entries for IPv4 and IPv6 loopback.
7. Issue a local mkcert certificate if one is missing.
8. Save the project into `devhelper.store.json`.
9. Optionally import a SQL dump after saving a successfully provisioned project.

Before steps 3 onward, creation validates input, checks project/domain/nginx ownership, validates any dump, and creates the selected database and user. A database failure returns an error before app/nginx/hosts/certificate files or successful metadata are written. Hosts and certificate permission/tool failures remain visible warnings. A dump that fails partway through also returns a visible warning while retaining the created project and credentials, so the user can repair or replace the import.

An operation lock serializes create/drop/import/repair across CLI and HTTP processes. Duplicate creation is rejected. New database names and usernames include company/project ownership and a hash, avoiding punctuation, separator and length collisions. Existing records retain their names and credentials. `db ensure` repairs missing databases from existing metadata without dropping data.

## Database Engines

The DB layer normalizes UI/CLI aliases before doing any work:

- `mysql` and `mysql-8.4` become `mysql-8.4`
- `mysql9`, `mysql-9.6`, and `mysql-9.7` become `mysql-9.7`
- `mariadb10` and `mariadb12` stay as named services
- `postgres` and `postgresql` become `postgres`

Each DB operation discovers the actual Compose services, starts only the selected service, and waits for an authenticated SQL query to succeed. Exact configured service names win; obsolete MySQL version names fall back to `mysql` / `mysql9` only when absent from Compose. Default clients run inside their matching container over TCP, avoiding client/version mismatches and temporary socket-only bootstrap servers. Explicit native clients still use configured host ports. Context cancellation and bounded startup/query timeouts propagate from CLI/HTTP, while dump imports can run longer. SQL travels over stdin and passwords through process environment rather than command arguments.

Deletion preserves metadata when database/filesystem deletion fails. `os.Root` confines file removal to configured roots. Shared legacy database or nginx ownership is rejected; shared legacy login users are retained during database deletion. Replacement rejects shared DB/user ownership and preflights the dump before dropping data.

Drop, replacement, and ensure also check other projects' local `db_connections` by normalized engine and database name. Observed secondary login names do not imply ownership of a managed login. External connections are excluded, while local secondary connections still count when their project's primary database is external. Ordinary imports retain their existing behavior without the shared-ownership check.

`db_external: true` rejects ensure, HTTP import/replacement, and CLI import before database access. Project deletion skips database cleanup for an external primary but can remove the project's local resources and store record. Secondary connections are dependencies, not additional databases to provision or delete.

## Store

The store is a single JSON file at `${DATA_ROOT}/devhelper.store.json`.

Database metadata distinguishes managed credentials from observed application configuration:

- `db`, `db_name`, `db_user`, and `db_pass` describe the primary database and its managed per-project credentials.
- `db_host` and `db_port` record the primary endpoint; `db_external` marks it as externally managed. Endpoint inventory does not override the configured Compose/native client targets.
- `db_connections` records dependency name, engine, host, port, database, observed user, external status, and configuration source. It contains no passwords; observed application users may differ from the managed primary user.

`internal/store` reads fresh disk state under native cross-process file locks. Mutations write a private temporary file, sync it and replace the destination only after a complete write. Failed writes do not truncate the old state or publish in-memory changes. Go's JSON v2 rejects duplicate keys and invalid UTF-8. Persistent `.lock` and `.operations.lock` sidecars coordinate readers/writers and multi-step operations; they must not be removed while a process uses the store.

## HTTP API

The web server embeds `internal/http/ui/*` and exposes:

- `GET /api/projects`
- `POST /api/projects`
- `POST /api/projects/drop`
- `POST /api/projects/import`
- `POST /api/cert/init`
- `POST /api/cert/issue`

The HTTP layer validates one bounded JSON document with strict fields, calls context-aware provisioning/store functions, and returns JSON responses. Go's cross-origin protection rejects browser-origin mutation requests. Chi routes requests and wraps responses for structured zerolog request/status/duration logs. The default listener is loopback; graceful shutdown drains active requests. Long imports are not cut off by a short HTTP write timeout.

The frontend source lives in `frontend/src`. React form actions manage pending, error and retry state. esbuild bundles React and Bootstrap into embedded static assets, removing runtime Babel and CDN dependencies. Go renders configuration metadata through an HTML template with safe JSON escaping.

## Git Hygiene

Runtime project data is intentionally ignored:

- `projects/apps/**`
- `projects/data/**`
- `projects/ssh/**`
- `projects/docker-compose.yml`
- generated nginx vhosts and local TLS material
- local dumps/backups/archives
- non-example `.env` files

The repository should contain templates, source code, and safe examples only.
